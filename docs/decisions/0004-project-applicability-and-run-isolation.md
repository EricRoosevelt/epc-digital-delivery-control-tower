## 2. 覆盖：三个粒度、两条轴（PM 裁定 1、2）

### 2.1 三个粒度，互相不能替代（PM 裁定）

| 粒度 | 回答的问题 | 数据从哪里来 | 由哪一层产生 |
|---|---|---|---|
| **要求 × 模型** | 这条要求对这个模型是否执行、是否返回了检查结果 | 本次运行的规则集、项目声明、finding | 验证层（覆盖记录） |
| **要求 × 成员** | 这条要求对这个成员——一个构件，或一对构件——读到了什么 | **只存在于 Purpose 评估记录的读数里**：admission、subscope 成员、`findings_for(element_key, requirement_keys)` 的结果，以及 `no-finding` / `not-applicable-finding` 两个缺席名 | Purpose 层（ADR 0003），不是验证层 |
| **构件整体** | 这个构件是否被**本次规则集**的任何检查结果触及 | 本次运行的 element 登记与 finding | 验证层（覆盖记录） |

三条约束（PM 裁定）：

- **"没有检查结果触及"不等于"从未被检查"。** 构件层记录的是"本次运行、本规则集，没有任何 finding 指向它"。它可能被别的规则集、别的运行、人工核查检查过；记录不对此作任何断言，措辞上也不能写成"未检查"。
- **成员层的来源只能是 Purpose 评估记录。** 验证层不读 Purpose 和 Overlay，这条既有边界不变；覆盖记录不计算、不推测成员层。**一次没有评估的运行，覆盖记录明确写"没有成员层"**，而不是把成员层留空或用构件层代替。
- **判定证据不能压成检查结果的计数。** 评估记录引用的人的判定（determination）按引用出现，有自己的出处与内容摘要；覆盖记录不把它折算进 PASS/FAIL/N/A 的任何计数，也不把"有判定"写成"已检查"。

### 2.2 "要求 × 模型"上的两条独立的轴（PM 裁定）

声明范围与实际执行是两件事，分成两条轴；**每条轴内恰好一类**，两条轴之间不要求互斥。

**声明轴**——关于这一对，事先声明了什么。两个字段，各自恰好一个值：

| 字段 | 取值 |
|---|---|
| 采用 | `adopted` / `not-adopted`（带理由） / `legacy-compat`（旧样例的兼容状态，见 P1）|
| 专业范围关系 | `inside`（模型声明的专业在规则范围内） / `outside`（在规则词表里但不在本规则范围内） / `unknown`（模型声明的专业不在任何规则的词表里，例如 `MEP`、`Facade`）|

**执行轴**——这一对实际发生了什么。恰好一个值：

| 取值 | 含义 |
|---|---|
| `not-executed` | 没有执行，**必须带原因**。今天唯一合法的原因是"未采用"。专业过滤不启用（P2），所以"因专业范围未执行"今天不存在。 |
| `executed-no-applicable-entity` | 执行了，实体筛选没匹配到任何构件（模型级 N/A）|
| `executed-with-results` | 执行了，返回 PASS / FAIL（带计数与谓词，见 P8）|
| `executed-no-result` | 执行了，却一条结果都没回来——兜底值，今天所有测量里都是 0（2.4 节）|

`outside` + `executed-with-results` 是合法组合，而且今天就存在：**R-001 作用在结构墙上，记为"范围不匹配，但已执行、PASS"**，不改记成"未检查"。过度检查因此保持可见。

## 4. 方案与实测对照

四个方案，每一个都在一次性检出里真的跑过（B、D、推荐方案的代码部分是一次性原型，只为测量，见证据说明）。

- **现状**：什么都不做。
- **方案 A — 运行隔离（零代码）。** 不属于已发布契约的项目不进 `projects/`，用它自己的配置或工作区跑。用到的全是已有的旋钮：`--config`、`--repository-root`、`[run] project_manifests`、`processed_data_dir`、`reports_dir`、`exporters`。
- **方案 B — 同一次运行内按项目派生验证身份。** 每个项目的 finding / issue 从只摘要本项目模型的 `validation_run_id` 派生；运行级 id 保留给 `run.json` 与产物包。
- **方案 D — 让 `discipline_scope` 直接生效。** 丢弃模型声明专业不在规则范围内的 finding。
- **推荐方案 R — A + 覆盖记录 + 采用声明。** 原型：`project.toml` 里一个 `[adoption]` 表（第 7 节说明它为什么不在 `[overlay]` 里）；未采用的要求不对该项目评估；覆盖记录写到任何已发布根之外；**不启用专业过滤**。

### 4.4 已发布项目若声明采用：实测为什么必须等

采用声明改变评估了哪些要求，所以它必须进入 `validation_run_id`。在**共享的已发布运行**里（证据 `SX`）：

|---|---|
| `pcert-sample` 声明"全部采用"，身份规则 = 每个决定都进身份 | 没有一条 finding 能变，却 **`iso-reference-view` 的 42 条 finding 0/42、4 个 issue 0/4 存活** |
| 同上，身份规则 = **只有"不采用"进身份** | **0 个文件变化**，121/121、21/21 |
| `pcert-sample` 声明不采用 R-009（不在冻结的 legacy 规则集 0.1 里） | 本项目少 9 条 finding、8 个 issue；**`iso-reference-view` 0/42、0/4**；legacy 不动 |
| `pcert-sample` 声明不采用 R-005A/B（在规则集 0.1 里） | **15 个文件移动，其中 8 个是 legacy 冻结产物**（`ids_findings.csv`、五份 `bcf_*.csv`、`ids_failures.bcf`、`run_manifest.json`），`epc-ct snapshot` 失败 |

由此得出、并经 PM 接受的三条：

1. **身份规则取"只有不采用进入 `validation_run_id`"，但它有前提**（PM 裁定）：
   - 采用声明必须先通过完整性校验——规则集里每条规则恰好一个决定，缺项、重复、未知项都在打开任何模型之前拒绝（原型实测：`missing ['R-010']`，0 个输出）；
   - 声明必须钉住规则集的 **id、版本与规范化摘要**。原型只钉了 id 与版本，**摘要钉住本轮没有实测**，是检查点 4 的验收项。钉住摘要之后，规则集新增一条规则就会让声明不再完整，从而先被拒绝，而不是被默认采用（P1）。
   - 身份相同**不抹掉治理上的差别**。`legacy-compat` 与"明确声明全部采用"得到同一个 `validation_run_id`（因为它们评估的要求集合相同），但覆盖记录把采用状态、完整的决定与理由按运行记下来（P7），两者在记录里不同，并且一次声明或理由的修改即使不改变检查结果的身份，也能在记录之间追溯到。
2. 在共享运行里，一个项目的采用决定会给**另一个**项目重新编号。所以采用声明只用于隔离运行里的项目，建立在运行隔离之上。
3. 已发布项目在 legacy 写出器退役（Phase 5）之前，保持 `legacy-compat`，不声明不采用任何规则。

## 5. 推进方案及其代价

### 5.0 现在就生效：运行隔离（零代码、零契约）

- **规则：** 已发布契约里的项目就是 `projects/*`，其项目集合的任何变化都走契约仪式（今天已经如此：CI 的 diff 闸门会因 canonical 字节变化而失败）。其他任何项目在自己的运行里跑；私有项目用仓库之外的工作区（`--repository-root`），这样它的名字、路径、字节一次也不进任何检出。
- **实测：** 已发布字节 0 变化（`SA`）；新项目在自己的运行里 exit 0；私有真实模型以工作区方式跑了 `check` 与 `run`（全部情景），一次性检出前后逐文件比较 **0** 差异。
- **代价（全部实测）：**
  - 工作区要带 `rules/` 的副本与 `third_party/` 下 BCF 3.0 schema 的副本；缺 schema 时 `run` 在写出 3 个文件之后 exit 1（`F7`）。规则副本会漂移，这正是检查点 4 要求钉住规则集摘要的原因。
  - 输出目录不能在仓库根之外：配置指向根外时，canonical 导出器先把 **12** 个文件写到根外，然后才以 `Export must stay inside the repository` 拒绝（`F6`）。所以隔离只能用工作区，不能只改输出目录。
  - 这一步只回答第三个问题；前两个问题要等下面的检查点。

### 5.1 四个检查点，依次推进，各自独立收口（PM 裁定）

每个检查点单独委派、单独一个 PR、单独审计；前一个没收口，后一个不开始。下面只写每个检查点要证明什么和不做什么，不替委派者定实现细节。

| # | 检查点 | 要证明 | 不做 |
|---|---|---|---|
| 1 | **覆盖记录** | 要求 × 模型层按 2.2 节的两条轴记录，每条轴内恰好一类；构件整体层按 2.1 节措辞记录；成员层在没有评估时明确写"没有成员层"；状态与谓词同时出现，拿不到可靠谓词时不单独显示 PASS、也不猜（P8）；拿不到可靠谓词的行在记录里怎么表示是本检查点的**技术待定**设计项（U11），不是 PM 裁定；记录与一次运行绑定、持久化在冻结发布树之外（P7）；已发布字节 0 变化；两次运行记录逐字节相同。此时还没有采用声明，所有已发布项目的采用字段为 `legacy-compat`。 | 不读 Purpose/Overlay；不改身份；不启用专业过滤；不进公开契约。 |
| 2 | **`check` 写入隔离** | `check` 默认不改用户的持久文件和仓库产物（今天写 13 个，6.1 节）；显式要求输出报告是可见的例外；`run` 的发布字节另行验证不变（P5）。 | 不改 `run` 的产物集合。 |
| 3 | **运行失败与产物一致性** | 五种结局分开呈现（P6）；失败时已发布根保持上一次完整交付的样子，不再出现 6.2 节 F3–F6 那样新旧混放的目录；BCF 上限保留，撞上限呈现为 `export-incomplete`。 | 不要求五个独立退出码；不取消、不放宽 BCF 上限；不做通用批次管理。 |
| 4 | **项目采用声明** | 规则粒度的 `[adoption]`（P1）；新项目必须完整声明，新增规则、缺项、未知项一律先拒绝；钉住规则集 id、版本与规范化摘要；只有不采用进验证身份（4.4 节的前提全部满足）；声明与理由的变化可在覆盖记录中追溯；未采用的要求不进 Purpose（7.2 节）。 | 已发布项目不声明任何不采用；不启用专业过滤。 |

检查点 1 在前，是因为后三个的"不许静默"都要靠它来证明：`check` 不写了、运行失败了、要求不采用了，每一种都必须在覆盖记录里有名有姓。

### 5.2 BCF 上限（PM 裁定）

- 上限保留。撞上限不是"CSV 成功、BCF 失败"，而是一次不完整的交付（6.3 节）。
- 先解决不适用的发现。实测：私有真实模型在现状下 1359 个 issue，其中绝大多数来自域裁定不适用的规则（4.2 节）；按 P4 裁定后为 0 个。
- 之后要用**一批正当的**大量 issue 验证交付规模——即适用规则下真实存在的大量问题，而不是不适用规则堆出来的数量。这一验证本轮没有做，也没有现成的数据（第 10 节 U9）。
- 不截断问题清单去凑上限；暂不做通用的批次管理。

### 5.3 推迟

- **方案 B**（契约 1.7）：只在产品需要"多个项目同一次已发布运行"时做。实测代价：一次性 0/121、0/21、21 份 markup、7 个文件，且必须升派生版本。之后加项目 121/121 存活，但共享文件仍被改写。
- **专业过滤**：PM 已裁定暂不启用（P2）。若将来启用，前提是显式多专业声明已经落地、覆盖记录已经存在，且被过滤的每一对都记为 `not-executed` 并带"专业范围"这一原因。

### 5.4 不需要的东西

不建通用配置平台：运行隔离只用已有的旋钮，`control-tower.toml` 不加键；采用声明是项目数据，落在它该在的 manifest 里（`AGENTS.md`"常量有三个家"）。不补规则标签或元数据，不加硬过滤，不改契约与快照。

## 6. `check` 的落盘承诺与失败呈现（PM 验收 4）

### 6.1 `check` 今天写什么

| 调用 | 写入（字节相同的重写也算写入） |
|---|---|
| `epc-ct check` | **13** 个文件：`reports/ids/` 下 12 个（每模型 `.html` + `.json`），外加 `ids/epc-delivery_v2.2.ids` |
| `epc-ct check --reports-dir <仓库外>` | 报告写到仓库外；仓库内仍重写 `ids/epc-delivery_v2.2.ids` |
| 加一个新项目后 `check` | 仓库内新增该项目每模型 2 个文件（合成项目 6 个） |

这 13 个文件都是已跟踪的生成产物，却**一个也不在 `artifact_manifest.json` 里**，也就不在 `artifact_bundle_id` 之内；只有 CI 的 git diff 闸门守着它们。

**PM 裁定（P5）：行为向承诺对齐。** `check` 默认不改用户的持久文件和仓库产物；显式要求输出报告是可见的例外；`run` 的发布字节另行验证。这是检查点 2。在它落地之前，`AGENTS.md` 已按"现状 / 目标"如实写明 `check` 今天会写文件（P9）。

### 6.2 失败后留下什么（实测）

| # | 失败 | 发生在 | 用户看到 | 仓库/工作区里留下 |
|---|---|---|---|---|
| F1 | 规划期拒绝（IFC2X3 模型；采用声明不完整） | 打开任何模型之前 | exit 1，`error: …` | **0** 个文件（探针 E1；本轮 `SR`） |
| F2 | 某个 checker 在某个模型上抛错 | `check` 阶段 | exit 1，**一段 Python traceback**（`CheckStageError` 不在 CLI 捕获的异常里） | 其他模型的 10 个报告与 `ids/` 下的编译文档被重写；失败模型的报告**没被重写**，磁盘上那份属于上一次运行 |
| F3 | BCF 上限 | 导出的第一个（导出器按 id 排序，`bcf` 最前） | exit 1，`error: BCF archive exceeds safe generation limits` | 新项目的 `reports/ids/` 文件 + `ids/` 文档；其余全部是**上一次运行的**产物，原样留着 |
| F4 | 后面的导出器失败 | 导出中段 | exit 1，`error: …` | canonical 9 个与 `issues.bcf` 来自新运行；失败的 `legacy-pbip` 没写，`artifact_manifest.json` 也没写，仍是旧运行的：清单写着旧 run id，**20 个哈希里 10 个与磁盘不符** |
| F5 | `--format` 只导出一部分（探针用的绕行） | — | **exit 0** | 清单诚实地只列实际运行的导出器（不含通用 BCF），但目录里的 `issues.bcf` 属于另一次运行，**24/24 条 finding 链接悬空** |
| F6 | 输出目录在仓库根外 | 导出之后 | exit 1 | 根外已写 12 个文件 |

另一个残留：`reports/ids/` 下已不存在的模型的报告从不被删除（证据脚本在 `SB` 段必须手动删除它们）。

### 6.3 具名结局：部分导出不是打折的成功（PM 裁定 P6）

一次运行只能以下列之一结束。**五种结局分开呈现，但不要求五个独立的退出码**（PM 裁定）：消息先说结局名，再逐个导出器列出"写了 / 没写 / 为什么"。

| 结局 | 条件 | 已发布根里 |
|---|---|---|
| `refused` | 规划期拒绝 | 不变 |
| `evaluation-incomplete` | 至少一个 checker 失败 | 不变（不再是 traceback） |
| `export-incomplete` | 验证完成，至少一个启用的导出器没写出 | **不变** |
| `complete` | 全部启用导出器写出，清单最后写出 | 整套替换 |
| `partial-by-request` | 用户用 `--format` 只要了一部分 | 明确不是交付，且不与旧产物混放 |

撞 BCF 上限就是 `export-incomplete`，原因写成"bcf：36 个 topic 所需条目超过 100 的上限"，不是"CSV 成功、BCF 失败"。`check` 应在结束时预告这一点——今天它对同一批数据报"36 issue(s)"并 exit 0，下一步 `run` 必然失败。如何做到"已发布根不变"（例如暂存后整套替换）、退出码怎样分组，是检查点 3 的设计，本文不定。

## 7. 与 Purpose / Overlay 的边界

### 7.1 验证层不读 Purpose 或 Overlay（边界 5，不变）

- `[adoption]` 是**验证层的项目数据**：它决定验证评估什么，属于"项目包含什么 → 它的 manifest"。它是 `project.toml` 的**顶层表**，不在 `[overlay]` 之下；验证层继续不读 `[overlay]`，Purpose 层也不读 `[adoption]`。两者恰好同在一个文件，是因为二者都是项目数据，不是因为它们是一层。
- 进入身份的只有"不采用"的 `(project_id, rule_id)`，只进 `validation_run_id`；不进 `requirement_key`、不进 legacy 身份。Purpose、Overlay 仍然不进 requirement、finding 或 legacy 的任何身份。
- "不采用"不是系统对适用性的判断：它是一个人做的、带理由的、被记录的决定，系统只引用它——与 BIM 一贯的"系统引用人的判断，从不代做"一致。它也不是 Purpose readiness、不是 blocker、不是 Overlay 的 evidence binding。
- 要求 × 成员层只存在于 Purpose 评估记录的读数里（2.1 节）。覆盖记录不从 Purpose 那里取它，没有评估时写"没有成员层"。

### 7.2 Purpose 的消费边界（PM 裁定；只写边界，不设计 Purpose）

- **新项目未采用的要求，不得被 Purpose 当成普通的"缺证据"继续评估。** 今天 Purpose 把"某个成员在绑定下没有 finding"读作结果 `not-yet-evaluated`、缺席名 `no-finding`（`epc_control_tower/purpose/assessment/reading.py` 的 `finding_backed_reading`）；一个因为项目明确不采用而没有执行的要求，如果走同一条路，会被读成"还没来得及检查"，而事实是"这个项目决定不要它"。这两件事必须分开。
- **首轮做法：直接禁止。** 在消费约束落实之前，带有 `not-adopted` 行的验证结果不进入 Purpose。
- **正式接通之前**，再以单独的检查点落实明确的消费约束（例如 Overlay 或 Pack 绑定到了一个未采用的要求时怎么处理）。本文不设计它。
- 已知交互：`pcert-sample` 的 Overlay 绑定了 R-005A/B；该项目保持 `legacy-compat`、不声明不采用（4.4 节第 3 条），所以今天不触发这条边界。

## 9. PM 的裁定（2026-09-29）

以下九条**都是 PM 的决定**，本文只记录，并注明各自落在哪个检查点。初版列出的选项与实测后果见 `e9d715a` 的本节；这里只保留与裁定相关的后果。P1–P4 对应 BIM 第八节第 1–4 条。

**P1 — PM 裁定：引入项目采用，规则粒度。**

- 每条规则恰好一个决定：`adopted` 或 `not-adopted`，后者必须带理由。
- **新项目必须完整声明。** 规则集新增的规则、声明里的缺项、声明里的未知项，一律先拒绝，**不默认采用**（原型实测：`missing ['R-010']` 在打开任何模型之前拒绝，0 个输出）。
- **旧样例**（`pcert-sample`、`iso-reference-view`）用一个明确标识的兼容状态 `legacy-compat`：意思是"这个项目没有作过采用决定，按兼容行为评估整套规则"。它**不伪装成已有的采用决定**——覆盖记录里写的是 `legacy-compat`，不是 `adopted`。
- 落点：检查点 4；`legacy-compat` 从检查点 1 起出现在覆盖记录里。

**P2 — PM 裁定：显式多专业声明；专业过滤暂不启用。**

- 一个模型可以显式声明多个专业；**不从 `MEP` 这类值、文件名或 IFC 类别去猜它包含哪些专业**。私有机电模型里有哪些专业的对象至今仍未核（U2），正说明不能猜。
- 专业过滤暂不启用。覆盖记录只在声明轴上写出 `inside` / `outside` / `unknown`，过度检查保持可见。
- 词表问题照实留着：规则用 `HVAC`、`Plumbing`，Pack 用 `from = "MEP"`。

**P3 — PM 裁定：R-001 / R-002 / R-006 可以作为本次内部探索的基础信息检查，并写明它们实际检查的谓词。**

| 规则 | 实际检查的谓词 | 不检查的 |
|---|---|---|
| R-001 | `IfcWall` 的 IFC `Name` 属性存在且非空 | 名字是否有意义、是否符合命名约定（私有模型 1134/1134 的名字是导出器按"族:类型:ElementId"生成的） |
| R-002 | `Pset_WallCommon.IsExternal` 存在，且数据类型是 `IfcBoolean` | **取值是否正确**（私有模型 1134 面墙全部为 `True`，包括内墙） |
| R-006 | 墙关联了材质、材质层集或材质构成集 | 关联的是什么材质、是否正确 |

落点：检查点 1 的谓词字段（P8）。

**P4 — PM 裁定：该私有项目不采用 R-005A/B、R-009、R-010；理由引用已有的域裁定。**

| 规则 | 理由（引用已有域裁定） |
|---|---|
| R-005A、R-005B | BIM 域评审在探针之前已裁定不得套用：它们是 `ProjectAssumption`，属于 `pcert-sample` 的 Overlay。 |
| R-009 | **BIM 已裁定它对该项目不适用**（上轮裁定，本轮维持）。它缺少 `ProjectAssumption` 标签是另一条独立的规则元数据缺陷，本轮不修，也不以它作为不采用的理由。 |
| R-010 | BIM 裁定：如其所写不适用——它的名字模式 `^(origin\|geo-reference)$` 是另一个项目约定的定位名。 |

- 理由**不能**写成"减少 issue、让运行通过"。issue 从 1359 降到 0（4.2 节）是这些裁定的后果，不是作出裁定的依据。
- **坐标确认的缺口继续具名保留。** BIM 裁定 R-010 提出的坐标参照问题本身对该项目适用，当前状态是 UNKNOWN、出口具名。不采用 R-010 只是说这条规则的写法不适用，不是说坐标已经确认：这个缺口必须以名字出现在 R-010 的不采用理由与该项目的覆盖记录摘要里，不能因为验证层少了一个载体而消失。
- **零 FAIL 不等于就绪。** P4 裁定后的运行是 0 FAIL、0 issue，而同一次运行里 2774 个构件没有被本次规则集的任何检查结果触及，坐标缺口仍开着。任何把这次运行呈现为"干净"或"就绪"的说法都不成立。

**P5 — PM 裁定：`check` 默认不改用户的持久文件和仓库产物；显式要求输出报告是可见的例外；`run` 的发布字节另行验证。** 落点：检查点 2。

**P6 — PM 裁定：五种结局分开呈现，但不要求五种独立的退出码。** 落点：检查点 3。

**P7 — PM 裁定：覆盖记录是内部记录，与某一次运行绑定。**

- 不进冻结发布树（`data/processed/`、`reports/`），不是公开契约。
- **也不能只打印出来就丢**：它要持久化在冻结发布树之外，与产生它的那次运行绑定。
- **采用声明或理由的变化必须能在记录里追溯到，即使检查结果的身份不变。** 例如只改了 R-010 的不采用理由，`validation_run_id` 不变（理由不进身份），但两次运行的覆盖记录必须能看出理由变了。
- 落点：检查点 1（记录本身）与检查点 4（采用声明进入记录）。

**P8 — PM 裁定：状态与谓词同时出现；拿不到可靠谓词时，不单独显示 PASS，也不猜。** 落点：检查点 1。这类行在覆盖记录里怎么表示不是 PM 的裁定，是检查点 1 的技术待定项（第 10 节 U11）。

**P9 — PM 裁定：在同一个 PR 里用单独一个提交，定向修正 `AGENTS.md` 的三处事实**，每处分开写"现状"与"目标"，不把尚未实现的能力写成现有的承诺：

1. 项目加入共享的已发布运行会重编其他项目的身份；
2. `discipline_scope` 目前在评估时不生效；
3. `check` 目前会写文件。

**不在本清单：** 开洞责任的协同边界与降板区（BIM 第八节第 5 条）——本轮明确不做。
