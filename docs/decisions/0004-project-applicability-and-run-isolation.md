## 2. 现状诊断：(a)–(e) 的定义与实例

### 2.1 粒度

BIM 的五种状态说的是"要求 R 在模型 M 的构件 E 上"。落到记录上需要两个粒度，每个粒度内**恰好一类**：

- **要求 × 模型对**（PM 验收的粒度）：每一对恰好是 (a)(b)(c)(d)(e) 之一。
- **构件**：每个构件要么被至少一条 finding 触及，要么是 (d)"无人触及"。

(d) 在两个粒度上都有意义，而且意思一致——"评估发生了，但这里没有结果"：

- **对粒度的 (d)**：R 对 M 被评估了，却一条 finding 都没回来。今天所有测量里都是 **0**，因为两个 checker 对每个被评估的对都至少返回一条 N/A 或 PASS/FAIL。它存在的理由是兜底：任何让 finding 静默消失的机制都会落进这一格而不是消失（2.3 节实测）。
- **构件粒度的 (d)**：构件 E 没有被任何 finding 触及——Checkpoint B case 4 的烟囱。

这个两粒度的读法是本文的解释，**请 BIM 在域审计时核对它是否就是 (d) 的原意**（第 10 节未知 U1）。

### 2.3 覆盖记录能否真的"不允许静默"：实测

原型覆盖记录（证据 `SR`、`SD` 段）对每个场景都做到了"每一对恰好一类"（`every row carries exactly one state: True`，已发布 84 对、合成项目 42 对、私有 42 对）。关键反例是 BIM 约束 3 担心的那种静默：把一个"让 `discipline_scope` 直接过滤 finding"的朴素实现（方案 D）与原型覆盖记录**同时**打开，合并 MEP 模型声明为 `Plumbing`，覆盖记录把被丢掉的 **37 对**全部记为 (d) `evaluated-no-outcome`，而不是让它们消失。没有覆盖记录时，同一次运行 exit 0，什么都不说。

新项目有两个版本：`S1` 是三个模型（撞 BCF 上限，所以身份与内容的比较用不含通用 BCF 的导出）；`S1b` 只有一个模型，BCF 写得出来。BCF 两行与"已发布文件"一行来自 `S1b`（其 `validation_run_id` 为 `…-c7f217dfae5e7c42`），其余来自 `S1`；两者在内容、`finding_key`、`issue_key` 三行上结果相同。

所以对用户的回答必须是两句话：**"其他项目的检查结果不变；其他项目的每一条 finding 和 issue 的编号都会变，BCF 里指向它们的链接也会变。"** 合成一句无论说"会"还是"不会"都是错的。机制已知：`build_validation_run_id` 摘要整次运行全部 `(model_key, content_sha256)`，`finding_key` 与 `issue_key` 再把它折进去。

复检联接不受影响（BIM 约束 9）：本文任何方案都不碰 `findings_for(element_key, requirement_keys)`。

## 4. 方案与实测对照

四个方案，每一个都在一次性检出里真的跑过（B、D、推荐方案的代码部分是一次性原型，只为测量，见证据说明）。

- **现状**：什么都不做。
- **方案 A — 运行隔离（零代码）。** 不属于已发布契约的项目不进 `projects/`，用它自己的配置或工作区跑。用到的全是已有的旋钮：`--config`、`--repository-root`、`[run] project_manifests`、`processed_data_dir`、`reports_dir`、`exporters`。
- **方案 B — 同一次运行内按项目派生验证身份。** 每个项目的 finding / issue 从只摘要本项目模型的 `validation_run_id` 派生；运行级 id 保留给 `run.json` 与产物包。
- **方案 D — 让 `discipline_scope` 直接生效。** 丢弃模型声明专业不在规则范围内的 finding。
- **推荐方案 R — A + 覆盖记录 + 采用声明。** 原型：`project.toml` 里一个 `[adoption]` 表（第 7 节说明它为什么不在 `[overlay]` 里）；未采用的要求不对该项目评估；覆盖记录写到任何已发布根之外；**不启用专业过滤**。

### 4.3 方案 D 的代价：把可见的过度检查换成不可见的漏检

合成合并 MEP 模型（PCERT 风管 + ISO 洗手盆），加一条一次性的 Plumbing 规则 R-P01，使两边各有一条规则可丢（证据 `SD`）：

| 合并模型声明为 | 全项目 findings | 全项目 issues | 在合并模型上静默消失的 |
|---|---|---|---|
| （不过滤） | 70 | 15 | — |
| `HVAC` | 32 | 13 | R-P01 的 PASS（洗手盆的空间归属，从此没人检查） |
| `Plumbing` | 24 | **10** | R-004A/B 的 3 条 PASS，**R-005A/B 的 6 条 FAIL**（这个模型上 3 个 issue 消失） |
| `MEP` | 22 | 10 | 这个模型上**全部 13 条规则**的结果，包括 R-010 |

三行里另外两个模型的损失相同：声明为 `Facade` 的模型不在任何词表里，它的全部结果（含 R-009、R-010 两个 issue）都消失；结构模型上 R-001、R-002 的 8 条 PASS 消失。

另外：`MEP` 与 `Facade` 不在任何规则的 `discipline_scope` 词表（`Architecture`、`HVAC`、`Plumbing`、`Structural`）里，而 Pack 的 `[[directions]]` 用 `from = "MEP"`。两套词表今天没有任何东西调和。**因此在 P2 有答案之前，本文不提出任何启用专业过滤的方案（BIM 约束 3）。** 覆盖记录只把关系写出来：`inside` / `outside` / `model-discipline-unknown`。

### 4.4 已发布项目若声明采用：实测为什么必须等

采用声明改变评估了哪些要求，所以它必须进入 `validation_run_id`。在**共享的已发布运行**里（证据 `SX`）：

| 情形 | 结果 |
|---|---|
| `pcert-sample` 声明"全部采用"，身份规则 = 每个决定都进身份 | 没有一条 finding 能变，却 **`iso-reference-view` 的 42 条 finding 0/42、4 个 issue 0/4 存活** |
| 同上，身份规则 = **只有"不采用"进身份** | **0 个文件变化**，121/121、21/21 |
| `pcert-sample` 声明不采用 R-009（不在冻结的 legacy 规则集 0.1 里） | 本项目少 9 条 finding、8 个 issue；**`iso-reference-view` 0/42、0/4**；legacy 不动 |
| `pcert-sample` 声明不采用 R-005A/B（在规则集 0.1 里） | **15 个文件移动，其中 8 个是 legacy 冻结产物**（`ids_findings.csv`、五份 `bcf_*.csv`、`ids_failures.bcf`、`run_manifest.json`），`epc-ct snapshot` 失败 |

结论三条：

1. 身份规则取"只有不采用进身份"。理由与 `identity.py` 自己的原则一致：验证身份只取决于能改变 finding 的东西，"采用"与今天的默认行为相同。代价：`未声明` 与 `声明全部采用` 共用同一身份，而覆盖记录上两者不同——若覆盖记录将来被发布，这个差别属于产物身份（与项目进度摘要进入 `artifact_bundle_id` 同一个道理），不属于验证身份。
2. 在共享运行里，一个项目的采用决定会给**另一个**项目重新编号。这就是为什么第 3 步必须建立在第 1 步（隔离）之上。
3. 已发布项目在 legacy 写出器退役（Phase 5）之前，不得声明不采用任何冻结规则集里的规则。

## 5. 最小推荐方案及其代价

### 第 1 步 — 现在：运行隔离（零代码、零契约）

- **规则：** 已发布契约里的项目就是 `projects/*`，其项目集合的任何变化都走契约仪式（今天已经如此：CI 的 diff 闸门会因 canonical 字节变化而失败）。其他任何项目在自己的运行里跑；私有项目用仓库之外的工作区（`--repository-root`），这样它的名字、路径、字节一次也不进任何检出。
- **实测：** 已发布字节 0 变化（`SA`）；新项目在自己的运行里 exit 0；私有真实模型以工作区方式跑了 `check` 与 `run`（全部情景），一次性检出前后逐文件比较 **0** 差异。
- **代价（全部实测）：**
  - 工作区要带 `rules/` 的副本与 `third_party/` 下 BCF 3.0 schema 的副本；缺 schema 时 `run` 在写出 3 个文件之后 exit 1（`F7`）。规则副本会漂移：采用声明钉住 `ruleset_id` + `version`（原型不一致即拒），实现时应再记录规范化摘要。
  - 输出目录不能在仓库根之外：配置指向根外时，canonical 导出器先把 **12** 个文件写到根外，然后才以 `Export must stay inside the repository` 拒绝（`F6`）。所以隔离只能用工作区，不能只改输出目录。
  - 这一步回答不了 (a)，也不给用户覆盖清单。它只回答第三个问题。
- **`AGENTS.md`** 里"Adding a project should not touch this package. Drop a directory under `projects/`"今天会让一个本地运行给所有已发布 finding 重新编号而 exit 0。建议改写（P9），本文不改。

### 第 2 步 — 第一个实现检查点：覆盖记录、`check` 不落盘、具名结局（代码，不动身份）

- 覆盖记录两个粒度（2.1 节），逐对写出采用状态、范围关系、状态、PASS/FAIL/N/A 计数。原型证明它能在不动任何已发布字节的前提下产生（`SR`：默认运行 0 个已发布文件变化；隔离运行连跑两次，输出与覆盖记录都逐字节相同）。
- 它是不是已发布产物，是 P7。**若不发布**：不走契约。**若发布**：新增文件、`artifact_manifest.json` 变化、快照刷新，即一次契约移动；其字节代价本轮**未测**，须在该检查点先测再走仪式。
- PASS 行可以从规则自己的 facet 推导出"检的是存在/类型，还是取值约束"（R-002 的 PASS 只说明属性存在且是 `IfcBoolean`；私有模型 1134 面墙全部为 `True`）。这不需要补规则元数据；是否呈现，是 P8。
- `check` 与失败结局见第 6 节。

### 第 3 步 — PM 裁定 P1、P4 之后：采用声明（代码，只用于隔离运行）

- `project.toml` 顶层 `[adoption]`：钉住规则集 id 与版本；**每条规则恰好一个决定**（`adopted` / `not-adopted`），`not-adopted` 必须带理由；缺、重、未知都拒绝，在打开任何模型之前（实测 0 个输出文件）。
- 未采用的要求不对该项目评估，覆盖记录里记为 (a) 并带理由。理由不进身份（改措辞不应重新编号）。
- 只有 `not-adopted` 进 `validation_run_id`，且没有项目声明时该成员不存在——实测已发布运行 0 字节变化。
- 契约：对隔离运行里的项目，不涉及已发布契约。已发布项目见 4.4 节：在 Phase 5 之前不声明任何"不采用"。

### 第 4 步 — 推迟

- **方案 B**（契约 1.7）：只在产品需要"多个项目同一次已发布运行"时做。实测代价：一次性 0/121、0/21、21 份 markup、7 个文件，且必须升派生版本。之后加项目 121/121 存活，但共享文件仍被改写。
- **专业过滤**：只在 P2 有答案、且覆盖记录已经存在之后。过滤掉的每一对必须记为 (b) 并带原因。

### 不需要的东西

不建通用配置平台：第 1 步只用已有的旋钮，`control-tower.toml` 不加键；采用声明是项目数据，落在它该在的 manifest 里（`AGENTS.md`"常量有三个家"）。不补规则标签或元数据，不加硬过滤，不改契约与快照。

## 6. `check` 的落盘承诺与失败呈现（PM 验收 4）

### 6.1 `check` 今天写什么

| 调用 | 写入（字节相同的重写也算写入） |
|---|---|
| `epc-ct check` | **13** 个文件：`reports/ids/` 下 12 个（每模型 `.html` + `.json`），外加 `ids/epc-delivery_v2.2.ids` |
| `epc-ct check --reports-dir <仓库外>` | 报告写到仓库外；仓库内仍重写 `ids/epc-delivery_v2.2.ids` |
| 加一个新项目后 `check` | 仓库内新增该项目每模型 2 个文件（合成项目 6 个） |

这 13 个文件都是已跟踪的生成产物，却**一个也不在 `artifact_manifest.json` 里**，也就不在 `artifact_bundle_id` 之内；只有 CI 的 git diff 闸门守着它们。`AGENTS.md` 与 CLI 帮助说 `check` "validate without writing anything"，与实测不符。

**建议对齐方向：行为向承诺对齐——`check` 在仓库内不写任何东西。** 理由：承诺是用户据以在工作树里对私有模型跑 `check` 的依据（探针就是这样在仓库里留下了私有命名的文件）；而"已发布产物只由 `run` 移动"正是硬规则 2 的本意。反方向（把文档改成"会写"）零成本，但留下的是一个会把私有名字写进仓库的命令。实现的形状：`check` 把 checker 报告与编译出的 IDS 写进临时目录，除非显式给了 `--reports-dir`；`run` 的字节必须不变——**这一点须在实现时实测**，本文未测。这是 P5。

### 6.2 失败后留下什么（实测）

| # | 失败 | 发生在 | 用户看到 | 仓库/工作区里留下 |
|---|---|---|---|---|
| F1 | 规划期拒绝（IFC2X3 模型；采用声明不完整） | 打开任何模型之前 | exit 1，`error: …` | **0** 个文件（探针 E1；本轮 `SR`） |
| F2 | 某个 checker 在某个模型上抛错 | `check` 阶段 | exit 1，**一段 Python traceback**（`CheckStageError` 不在 CLI 捕获的异常里） | 其他模型的 10 个报告与 `ids/` 下的编译文档被重写；失败模型的报告**没被重写**，磁盘上那份属于上一次运行 |
| F3 | BCF 上限 | 导出的第一个（导出器按 id 排序，`bcf` 最前） | exit 1，`error: BCF archive exceeds safe generation limits` | 新项目的 `reports/ids/` 文件 + `ids/` 文档；其余全部是**上一次运行的**产物，原样留着 |
| F4 | 后面的导出器失败 | 导出中段 | exit 1，`error: …` | canonical 9 个与 `issues.bcf` 来自新运行；失败的 `legacy-pbip` 没写，`artifact_manifest.json` 也没写，仍是旧运行的：清单写着旧 run id，**20 个哈希里 10 个与磁盘不符** |
| F5 | `--format` 只导出一部分（探针用的绕行） | — | **exit 0** | 清单诚实地只列实际运行的导出器（不含通用 BCF），但目录里的 `issues.bcf` 属于另一次运行，**24/24 条 finding 链接悬空** |
| F6 | 输出目录在仓库根外 | 导出之后 | exit 1 | 根外已写 12 个文件 |
| F7 | 工作区缺 BCF schema | BCF 导出 | exit 1 | 3 个文件 |

另一个残留：`reports/ids/` 下已不存在的模型的报告从不被删除（证据脚本在 `SB` 段必须手动删除它们）。

### 6.3 建议：具名结局，部分导出不是打折的成功

一次运行只能以下列之一结束，每种有自己的退出码，消息先说结局名，再逐个导出器列出"写了 / 没写 / 为什么"：

| 结局 | 条件 | 已发布根里 |
|---|---|---|
| `refused` | 规划期拒绝 | 不变 |
| `evaluation-incomplete` | 至少一个 checker 失败 | 不变（不再是 traceback） |
| `export-incomplete` | 验证完成，至少一个启用的导出器没写出 | **不变** |
| `complete` | 全部启用导出器写出，清单最后写出 | 整套替换 |
| `partial-by-request` | 用户用 `--format` 只要了一部分 | 明确不是交付，且不与旧产物混放 |

要做到"不变"，导出器写到暂存目录，全部成功后整套替换，清单最后写；失败就丢弃暂存。**BCF 上限保留**：撞上限就是 `export-incomplete`，原因写成"bcf：36 个 topic 所需条目超过 100 的上限"，不是"CSV 成功、BCF 失败"。`check` 应在结束时预告这一点——今天它对同一批数据报"36 issue(s)"并 exit 0，下一步 `run` 必然失败。具体形状、退出码数值与措辞是 P6。

## 7. 与既有边界的关系：验证层不读 Purpose 或 Overlay（边界 5）

- `[adoption]` 是**验证层的项目数据**：它决定验证评估什么，属于"项目包含什么 → 它的 manifest"。它是 `project.toml` 的**顶层表**，不在 `[overlay]` 之下；验证层继续不读 `[overlay]`，Purpose 层也不读 `[adoption]`。两者恰好同在一个文件，是因为二者都是项目数据，不是因为它们是一层。
- 进入身份的只有"不采用"的 `(project_id, rule_id)`，只进 `validation_run_id`；不进 `requirement_key`、不进 legacy 身份。Purpose、Overlay 仍然不进 requirement、finding 或 legacy 的任何身份。
- "不采用"不是系统对适用性的判断：它是一个人做的、带理由的、被记录的决定，系统只引用它——与 BIM 一贯的"系统引用人的判断，从不代做"一致。它也不是 Purpose readiness、不是 blocker、不是 Overlay 的 evidence binding。
- **已知交互，本轮不设计：** 若某项目的 Overlay 绑定了该项目未采用的要求，Purpose 层读到的是 `no-finding`。`pcert-sample` 的 Overlay 正绑定了 R-005A/B。今天不会发生（4.4 节第 3 条：已发布项目不声明不采用），但 Purpose 层将来需要一条拒绝规则。本轮不碰 Purpose（第 8 节）。
