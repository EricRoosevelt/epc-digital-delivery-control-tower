# Doctor 首次检查路径

日期：2026-10-02。负责：Product/UI Engineer。状态：可点击版本，待同一位经理短测；未收口。
它接在[可用性修订](2026-10-01-doctor-usability-revision.md)之后，取代那一版的主路径。

## 为什么又改

第二次用户验收仍然没过。根本原因是页面回答的是“记录里有什么、哪些话不能误读”，不是“我现在该做什么”。
这一版改的是组织方式，不是再补解释句：

> 首次检查 → 找到需要处理的事 → 看清对象、处理方和动作 → 再看同一事项的复检变化。

验收看这位经理能不能自己找到事项并说出具体行动。这份文档和测试都证明不了这一点。

## 路径的每一屏

| 屏 | 地址 | 说什么 |
| --- | --- | --- |
| 首页 | `#/` | 没有改框架，只把示例入口的说明改成“从一次首次检查出发”。 |
| 示例目录 | `#/fixture` | 两个写好的示例，标着“第一步”“第二步”：一次首次检查，然后是同一份记录的复检。 |
| 首次检查结果 | `#/fixture/member-evidence` | 先一句结果：共多少个事项、多少个需要处理，受阻和无法判断各多少（分开计，不合称）。然后按处理团队分组：每个团队一张小表（问题、哪项工作和结论、事项数）和它的事项卡片。再列记录没有给出后续处理动作的事项，每行是“构件｜那项工作：可以开始”加它旁边的限制。最后是去复检示例的入口、“如何阅读”、追溯信息。 |
| 首次检查事项 | `…/item/<工作>/<组>/<项>` | 一、结论（哪项工作、结论、依据来源、旁边的限制）；二、是哪两个构件；三、要做什么、由谁处理、完成后拿什么复检；四、具体缺什么（只在结论引用了检查结果时出现）；然后：这一项复检后的变化。依据逐条、如何阅读、追溯信息折叠。 |
| 复检事项 | `…/recheck/of/<工作>/<组>/<项>` | 同一事项在复检记录里：结论写成“复检前 受阻 → 现在 可以开始”或“受阻（复检前后未变）”；其余结构与首次检查事项相同，多一节“复检前留下的结束条件，这次达到了吗”和一节“复检前的证据”。 |
| 复检结果 | `#/fixture/recheck-requirement-relaxed` | 与首次检查结果同一套写法；开头列出结论和复检前不同的事项。 |
| 检查没有开始 | `#/real/real-refusal` | 原因、要让检查能够开始需要什么；系统的英文原文和拒绝码折叠。 |

## 留在结论旁的限制，和它出现的条件

| 限制 | 出现的条件 |
| --- | --- |
| “这个结论建立在模拟证据上：”加逐类来源标注 | 这个结论引用的证据里，任何一条带 `fixture` 标记。按每条引用自己的标记判定，不看记录的 `mode`。 |
| “示例处理团队” | 返回数据的 `mode` 是 `fixture` 时，标在每个团队旁。 |
| “处理团队是记录里的安排，不代表已经派发” | 每次显示处理团队时。 |
| “只对这一个事项、这项工作、所列的模型版本成立；不代表整次交接完成” | 结论是可以开始时。 |
| “规则只证明构件有楼层或空间归属，没有验证接收方模型有对应楼层”和“这个结论靠的是两侧模型的对齐确认，不是共享定位标记通过” | 吊顶平面与包封布置这项工作的结论是可以开始时。 |
| “‘无法判断’……不等于这个构件没有问题，也不是系统出错” | 结论是无法判断时。 |
| “资产标识是本项目约定的要求……取值从哪里来、对应哪个 Revit 参数，记录未提供” | 问题类型是两个资产标识类型之一时。 |
| “和这一项放在一起评估的旧证据里，有 N 条的检查要求变了” | 复检记录里，同组旧证据行带 `requirement-semantics` 变化时。 |
| 构件不在了、不再配成一对等“不等于修复”的说法 | 复检记录里，这个事项的去向不是“仍在范围内”时。 |
| 模型重新发布“不代表修复已经发生” | 复检记录里，有一侧模型重新发布时。 |

## 收进“如何阅读”的

一个事项是什么、为什么事项数不是缺陷数；三个判断词各自的完整定义和适用范围；四种证据来源标注的完整句子；
处理团队与默认处理角色的区别；复检页另有原来每页都显示的五句（比较依据一致不代表不用复核、
只有模型版本变了不等于结果变了、无法比较不是证据缺失等）。

## 主界面上仍留着的代码或英文

| 留着的 | 在哪 | 为什么 |
| --- | --- | --- |
| 团队和角色代码（`coordination-team`、`model-coordination`） | 汇总、事项页 | 记录只带代码，没有可读名称。 |
| 构件名称（英文） | 所有构件 | 来自样例模型文件本身。 |
| IFC 类别名（`IfcChimney`） | 构件旁的小字 | 中文类别名是本界面加的，留着供核对。 |
| GlobalId、内部键 | 构件卡片 | 在模型里定位用。 |
| `pcert-sample`、`MEP → Architecture`、`hvac`、`architecture` | 顶栏、构件卡片 | 项目、交接角色和模型的标识。 |
| 英文的动作和复检条件 | 只在记录的规则版本不是 0.1.0 时 | 中文句只为那一个版本写；其他版本照登原文。 |

判断词的英文、活动和问题类型的代码、英文原文、引用键，都在折叠的追溯信息或“规则原文”里。

## 没有做、在等的

- **“具体缺什么”还没有内容。** 这一节只从返回数据的 `finding_details` 取。现在返回数据里没有它，页面写“记录未提供”。
  界面不读规则文件，也不写取值、Revit 参数名或导出映射。核心侧带出这份数据之后再接。
- 其余九个复检示例、记录页、明细页、成员页没有改。
- 首页框架没有动。
