## 1. 要支持的主张

经理在现有 Doctor 里打开一次真实检查，能找到那一项、指出要回到 Revit 改哪个对象；看复检后能说清什么变了、
为什么变、还缺什么证据；看一条通过，能说出它证明了什么、没证明什么。

技术检查只验证数据和呈现边界。上面的主张要由经理的真人操作来验证，本文件没有这项证据。

## 2. 屏幕

| 屏幕 | 路由 | 回答什么 | 数据来源 |
| --- | --- | --- | --- |
| 首页卡片 | `#/` | 服务器有没有带工作区启动 | `/api/runs?mode=workspace`；没有运行就没有卡片，问询失败就说问询失败；有运行时，首页提示改说同时提供真实检查和示例 |
| 结果页 | `#/workspace/workspace` | 各结果的条数、检查了哪条要求及其出处、逐条结果列表 | `run`、`findings`、`requirements`、`elements` |
| 单条结果（在结果页右侧） | `…/finding/<finding_key>` | 结果 → 回 Revit 找哪个对象 → 改什么（仅不通过）→ 具体要求与观察 → 与前一次比 | 同上，加 `comparison` 里这一条所在的配对 |
| 前后对比 | `…/compare` | 两个运行号与谁被指定为前一次；什么变了；为什么会变（返回数据能说明的部分）；还缺什么证据 | `comparison` 原样：`pairs`、`not_re_evaluated`、`newly_appearing`、`changed_models`、`prior_run` |
| 对比被拒绝 | 同结果页路由，`outcome: "refusal"` | 不能对比的全部原因，以及要能对比需要什么 | `refusal.reasons`，每个拒绝码一句中文，原文折叠 |
| 程序故障 | 同上，请求失败时 | 程序没有拿到数据 | 原有故障屏，技术信息原文 |

布局：结果页在宽屏上左列表、右详情（参考 [ifcqa-tool 的问题详情交互](https://github.com/tommylee0923/ifcqa-tool/blob/517654cb79c8ba9acd213a3542e877f5929ce626/frontend/src/components/IssueDetail.tsx)：
列表与详情联动、要求与观察在同一处；没有复制任何代码，也没有引入第三方代码）。
窄屏上选中的详情排在列表前面。列表可按结果筛选，也可按 IFC Tag、名称或 GlobalId 查找；筛选条件在列表与详情之间来回时保留，换一次运行就清空。
结果词是检查自己的三个：通过、不通过、不适用；形状靠边框（实线、虚线、点线），不靠颜色。

## 3. 界面做什么、不做什么

- **不计算对比。** 配对、未再评估、新出现、哪些模型变了，都取返回数据。界面只把配对按“前一次结果 → 本次结果”归组并计数，
  只有一边有的行另列、另计，永远不算进配对。`tests/test_doctor_workspace_screens.py` 用真实运行核对：各组条数之和等于配对数，
  每组里的每一行都是返回数据里的那一行；读取 `comparison.pairs` 的只有 `workspace-model.js` 一处。
- **不出现“已修复”“已解决”。** 为这些页面写的每一句都不含“修复、修好、解决、改善”，也不含“受阻、无法判断”（测试逐句检查）。
- **没有交接判断。** 页首上下文栏、结果页和对比页开头都写明“只有检查结果，没有交接判断”；页面不调用任何交接判断词的显示函数（测试检查）。
- **产品验证规则的身份取自返回数据。** “这是一条产品验证规则”只在要求的 `labels` 含 `ProductValidation` 时出现；出处是返回数据的 `citation` 原文，
  逐字匹配时旁边给中文。界面不自己断言来源。
- **通过不带观察值。** 通过的检查结果 `actual` 为空；页面写“通过的检查结果不带它读到的值：只记录了‘要求已满足’”，不写读到了什么。
  任何一句都不写“读到的是……”（测试检查）。
- **规则说明只对它写给的那个版本成立。** `RULE_NOTES` 只在运行的规则集是 `product-validation` 1.0、规则是 `PV-001` 时使用；
  其他规则集或版本只显示英文原话，并说本界面没有为它写说明（测试改版本号核对）。
- **新句子全部进词表。** `workspace-screens.js` 里除沿用的“返回首页”外没有一个汉字（测试检查）；可读副本在
  [复检词表第 14 节](2026-10-02-doctor-recheck-vocabulary.md)，测试逐句核对两者一致。

## 4. 留在结论旁的限制与出现条件

| 限制 | 出现在哪里 | 出现条件 |
| --- | --- | --- |
| 只有检查结果，没有交接判断 | 上下文栏；结果页、对比页开头 | 工作区的每一屏，始终 |
| 返回数据的标签标明这是一条产品验证规则 | “检查了什么”里每条要求 | 该要求的 `labels` 含 `ProductValidation` |
| 出处原文（及逐字匹配时的中文） | 同上 | 要求带 `citation` 时始终 |
| 它证明：读到的预定义类型属于四值之一 | 通过的详情，结论正下方，展开 | 状态为通过，且规则说明适用（product-validation 1.0 / PV-001） |
| 它不证明：取值正确（写成 GRILLE 也会通过）、墙上有对应的洞口、风口所在的模型与外墙所在的模型已经对齐、任何工作可以开始 | 同上 | 同上 |
| 检查器会先把 USERDEFINED 换成自由文本再比较，文本拼成 LOUVRE 也会通过 | 同上 | 同上 |
| 通过的检查结果不带它读到的值 | 同上 | 状态为通过且 `actual` 为空；`actual` 非空时改写“带有观察值，本页不显示取值” |
| 通过能证明到哪里，本界面没有为这条规则写说明 | 通过的详情 | 状态为通过，规则说明不适用 |
| 不适用不是通过 | 不适用的详情 | 状态为不适用 |
| IFC Tag 通常是 Revit 的 ElementId，本页不能确认这一对应，选中后请核对名称和类别 | 单条结果“回 Revit 找哪个对象” | 这个构件带 `tag` |
| 没有 Tag 的原因 | 同上；列表里用短语 | 没有 `tag`：按模型的 `tag_source`（文件里没写／未找到模型文件／模型文件版本不同），`tag_source` 缺失时说来源未说明 |
| 取哪个值、由谁决定和操作、用哪个 Revit 参数写出，返回数据没有提供 | 单条结果“要改什么” | 状态为不通过，且规则说明适用 |
| 哪一次在前是启动时的指定，返回数据不能证明先后 | 对比页“两次运行” | 有对比时始终 |
| 在 Revit 里改了什么、取值由谁决定、由谁操作，返回数据没有记录 | 对比页“还缺什么证据” | 有对比时始终 |
| 外墙洞口要协调评审判定、对齐要对齐确认记录、分类判断要另行记录 | 同上 | 规则说明适用时 |
| 只在前一次有结果的不是通过 | 对比页 | 有这样的行时 |

## 5. 用私有区两次运行走过的记录（只写计数）

服务器从本分支的工作树启动，`--workspace` 指向私有区的工作区（修改后），`--prior` 指向私有区存下的修改前结果。浏览器内置面板，1400 宽、800 宽、375 宽各看一遍。

- 首页：出现第三张卡片“查看一次真实检查”；不带工作区启动时只有原来两张。
- 结果页：共 98 条——不通过 94、通过 2、不适用 2（不适用的 2 条是两个没有适用构件的模型各一条）。
  检查了 1 条要求，标签显示为产品验证规则，出处原文与中文并列。构件 4898 个，其中 4797 个带 IFC Tag。
- 按尺寸关键字查找，列表剩 4 条（目标类型 2 条通过、对照类型 2 条不通过）；按一个 Tag 查找剩 1 条。点开后筛选条件保留，焦点落在详情标题。
- 通过的详情：结论“通过”，下方展开“它证明／它不证明”四条和 USERDEFINED 一句，以及“不带它读到的值”；IFC Tag 及核对说明、名称、类别（风口）、楼层、模型、文件、GlobalId；
  与前一次比：前一次不通过、本次通过，两次原因原文并列。
- 不通过的详情（对照类型的一个实例）：多出“要改什么”四行；与前一次比两边都是不通过。
- 对比页：两个运行号，前一次标为“启动时用 --prior 指定”；两次结果不同 2 条（不通过 → 通过 2），相同 96 条（不通过 → 不通过 94、不适用 → 不适用 2），
  未再评估 0，新出现 0；内容变了的模型 1 个，内容未变 2 个。
- 把两个目录对调启动：对比页变成“通过 → 不通过：2 条”，没有任何额外说法；当前一侧的模型文件不在那个目录下，Tag 一列显示“未找到模型文件”，详情里是整句。
- 375 宽：没有横向滚动，选中的详情排在列表之前。
- 原有路径回归：模拟示例目录、首次检查结果、复检结果、随附项目的检查尝试都照常打开；页首提示带上了“证据方法的接受”，一个事项页显示“须重新出具”。

## 6. 对比被拒绝、程序故障各是什么样

- **对比被拒绝**（用公开样例造的两个工作区：本次用产品验证规则集，前一次用随附规则集）：标题“这两次运行不能对比”；
  五个原因各一句中文加拒绝码（规则集不同、版本不同、内容不同、要求不是同一组、检查程序不同）；“要能对比，需要什么”两段，
  包括去掉 `--prior` 只看本次结果；“没有任何结果、零问题统计或完成比例”；系统原文折叠。上下文栏写“本次没有检查结果”。
- **程序故障**（`--workspace` 指向一个没有跑完检查的目录）：原有故障屏“程序故障：没有拿到检查数据”，技术信息原文是
  `FileNotFoundError: … holds no finished run`，没有任何关于项目或模型的话。
- 返回数据形状不符（缺 `run`、`findings` 等，或拒绝里带了结果）也走故障屏，说明缺的是哪个键。

## 8. 仍说不准的措辞（请 BIM 核）

2026-10-03 经理走查前的修正（分支 `fix/doctor-c2-wording-before-manager-walk`）关闭了第 2、3、6 项，
并按 BIM 的第三条约束改了“要改什么”的第一句（列为第 8 项，请复核）；新旧原句见
[复检词表第 15 节](2026-10-02-doctor-recheck-vocabulary.md)。第 1、4、5、7 项原样留给 BIM。

1. **（未关闭）** **“在 Revit 的类型上改值，会作用于这个类型的全部实例。”** 这是 Revit 的常识与本次源修改的实测，不是返回数据的内容；
   它也没有说要用哪个参数（本次实际用的机制只试过一种，页面不写）。
2. **（已关闭）** **IFC Tag 的核对说明**“只在个别对象上从 Revit 界面核对过”说的是这个项目的核对历史，返回数据里没有；
   换一个工作区，这句话不一定成立。
   现在：“本页不能确认这一对应：选中后请核对名称和类别。”不讲核对历史，任何工作区都成立。
3. **（已关闭）** **“风口对应的外墙洞口：需要两侧一起做协调评审判定。”** BIM 原文写的是“机电与建筑一起”；现有测试禁止词表里出现专业名
   （防止从模型标识推断专业），所以改成“两侧”。是否需要点名专业，请 BIM 定。
   现在：按各自持有什么来称呼——“需要风口所在模型和外墙所在模型的持有方一起做协调评审判定”；“它不证明”和“还缺什么证据”里的
   “两侧模型”同样改为“风口所在的模型与外墙所在的模型”。工作区各页不再出现“两侧”（测试检查）。页面上的专业名只有返回数据里
   项目清单声明的 `discipline`，原样显示在模型名旁。
4. **（未关闭）** **“NOTDEFINED 等于什么都没说。”** 取自规则的 `instructions` 与 BIM 原文；返回数据不带 `instructions`。
5. **（未关闭）** **“取值是否选对：分类判断要另行记录；检查通过不能反过来证明分类判断正确。”** 依据产品任务书 10.4，语气是否合适。
6. **（已关闭）** **首页的“当前为示例预览”**一句没有改：带工作区启动时，首页同时有真实检查和示例，这句话变得不全对。产品决定是否改。
   现在：带工作区启动时改说“当前同时提供两样：启动服务器时指定的工作区里一次已经跑完的真实检查，以及模拟示例。
   页面上不能导入、选择或更换模型，也不提供整体合规或可施工结论。”不带工作区时仍是原句。
7. **（未关闭）** 原因原文 `The predefined type "NOTDEFINED" does not meet the required type` 的中文“预定义类型‘NOTDEFINED’不满足要求的类型”
   是逐字翻译；公开样例里 USERDEFINED 换成自由文本后的原因（引号里是自由文本）没有中文，按原文显示。
8. **（已改，请 BIM 复核）** “要改什么”的第一句原为“把它在 IFC 里的预定义类型写成 DIFFUSER、GRILLE、LOUVRE、REGISTER 之一，
   重新导出，再检查。”现在从 Revit 源头说起：“回到 Revit 源模型，让这个风口导出后的预定义类型是 DIFFUSER、GRILLE、LOUVRE、REGISTER 之一；
   重新导出 IFC，再检查。”不写用哪个参数或导出机制。同一格里的“NOTDEFINED 等于什么都没说”就是第 4 项，没有动。
