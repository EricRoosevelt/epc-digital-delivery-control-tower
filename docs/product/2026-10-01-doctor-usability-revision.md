# Doctor 可用性修订：先做通一条路径

日期：2026-10-01。负责：Product/UI Engineer。状态：这一版的主路径在第二次验收后被[首次检查路径](2026-10-02-doctor-first-check-path.md)取代；下面是当时的记录。

## 为什么有这一轮

复检界面的用户走查没有通过：BIM 经理读不懂界面。这一轮不改评估语义，只改这位经理要走的一条路径，
先确认方向，再扩展到别的示例和页面。

> 首页看懂用途 → 选一个看得懂的示例 → 找到待处理事项 → 看清是哪两个对象 → 明白依据与下一步。

验收不看测试数量，看这位经理不靠讲解能不能自己说清用途、找到事项、明白下一步。这份文档和测试都证明不了这一点。

## 路径的每一屏

| 屏 | 地址 | 说什么 |
| --- | --- | --- |
| 首页 | `#/` | 标题“查看模型交接中仍需处理的事项”；一句话说服务谁、回答什么；紧接着一条始终可见的提示：示例预览，不能导入自己的模型，不提供整体合规或可施工结论。然后是“现在可以做什么”（两个入口）和“现在还不能做什么”。 |
| 示例目录 | `#/fixture` | 一个写好的示例：名称、它回答的问题、标着“示例说明”的一句“这个示例被给了什么”，并说明示例说明不是检查得出的结论。其余示例列在下面，注明本轮没有改到。 |
| 结果页 | `#/fixture/recheck-requirement-relaxed` | 先“本次结果”：多少项记录给出了下一步、模型有没有重新发布、哪些判断和复检前不同（直接链接到那一项）。再“待处理事项”逐项列出。记录没有给出下一步的事项折叠在下面。然后是必须读到的限制、复检前后什么变了、追溯信息。 |
| 事项页 | `…/recheck/<组>/<项>` | 标题是构件名称（一对构件写“甲 与 乙”）。一、现在的判断（接收方的哪项工作、判断词和它对这项工作的含义、得出判断的读数）；二、是哪两个构件；三、下一步；四、复检前留下的结束条件这次达到了吗；限制；五、依据逐条；追溯信息。 |
| 检查尝试 | `#/real/real-refusal` | “这次检查尝试没有开始评估”，先用中文说项目条件哪里没满足，再给拒绝码和系统原文。 |
| 程序故障 | 任何请求出错时 | “程序故障：没有拿到检查数据”，说明这不是对项目或模型的判断，附技术原文。与上一屏不共用任何措辞。 |

选的示例是 `recheck-requirement-relaxed`：两侧模型都没变，有一项判断从 BLOCKED 变成 READY，
同时有一对构件（烟囱和屋顶）的问题原样留着。它一份记录里同时有“变了的”和“还要处理的一对对象”。

## 四个取舍

**示例说明和记录结论分开。** 目录里的“这个示例被给了什么”是搭示例的人的话，只出现在目录，带“示例说明”标签。
结果页只说记录支持的内容：示例名“模型未改，但交接判断发生变化”两半都是记录里有的（没有模型重新发布；有一项判断不同），
“检查要求放宽了”这句不在记录里，所以不出现在结果页——结果页只说“检查要求变了”，并说记录不说明是放宽还是收紧。
这取代了“运行名只能是编号”的旧规则；`test_an_example_is_described_in_the_directory_and_nowhere_else` 固定新的界线。

**“待处理”是记录给出了下一步，不是界面的判断。** 事项按“记录为它指出的当前位置上有没有下一步”分三组。
界面不看 READY / BLOCKED / UNKNOWN 这些词来分组，也不给总状态或评分。

**不进折叠区的三样东西没有动。** 模拟提示（顶栏下方，每一屏）、每条引用旁的来源标注、五句限制，都在展开的页面上。
折叠起来的只有：记录没有给出下一步的事项列表，和追溯信息（内部键、指纹、记录原码）。

**构件只说拿得到的。** 名称、类别、楼层、GlobalId、所属模型。专业拿不到，卡片上直接写“记录未提供专业信息；
本界面不从模型标识推断专业”；所属模型旁写“这是模型标识，不是专业声明”，并写它在本次交接中是交出方还是接收方的模型
（取自记录的模型版本比较，是交接角色）。

## 主界面上还留着的内部用语

| 留着的 | 在哪 | 为什么 |
| --- | --- | --- |
| `READY` / `BLOCKED` / `UNKNOWN` | 结果页、事项页 | 是记录给出的判断词，换掉就成了界面自己的结论。旁边加了中文说明。 |
| 英文的下一步、复检条件、系统拒绝原文 | 事项页、检查尝试页 | 是交接判断规则和系统给出的原文。界面不翻译，标明“记录原文，英文”；问题类型另有界面的中文说明。 |
| IFC 类别名、活动与问题类型的代码 | 中文说明旁的小字 | 中文是本界面加的说明，代码留着供核对。 |
| 英文的构件名称 | 所有构件 | 来自样例模型文件本身。 |
| 角色与团队代码（`architecture-lead`、`architecture-design-team`） | 事项页“下一步” | 记录携带的就是代码，没有可显示的名称。 |
| `pcert-sample`、`MEP → Architecture`、`hvac`、`architecture` | 顶栏、构件卡 | 项目、交接角色和模型的标识，取自记录。 |
| 引用键（UUID、`fixture-determination/…`） | 事项页“依据” | 逐条来源标注必须贴着它所标注的那条引用。 |
| 记录页、明细页、成员页的全部旧用语 | 从“追溯信息”和“下一步”里的链接进入 | 本轮没有改这三页；链接旁注明“该页尚未改版，仍是内部用语”。 |

## BIM 领域审计之后改的（2026-10-02）

`aa1129b` 的审计结论是有风险：中文说明把“这项工作能否开始”说成了“检查是否通过”。改了七处，逐句出处见
[复检词表第 11 节](2026-10-02-doctor-recheck-vocabulary.md)：

1. 三个判断词的说明带上对工作的后果和评估范围（Checkpoint B 第 1 节）。
2. 活动不再叫“检查内容”，叫“接收方的哪项工作”，并写这项工作需要交接提供什么；Pack 不再叫“检查清单”。
3. 记录显示同组旧证据里检查要求变了时，这件事写在判断词下方（列表卡片、事项页、结果块三处），不只在依据区。
4. 判断旁显示记录给出的终点读数；READY 来自“不穿过任何构件”时明说开洞情况没有被评估。
5. `in-model-position-*` 一律说成楼层归属。
6. 复检条件的标签是“复检要显示什么，这一项才算结束”。
7. Pack 的十个问题类型全部有说明；有测试对照 Pack 文件，缺一个就失败。

首页框架和“待处理”的分组范围没有动，等产品决定。
